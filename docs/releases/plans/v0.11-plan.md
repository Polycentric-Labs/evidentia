## Sequencing constraints (why the waves are ordered this way)

1. **The OSCAL 1.2.1 → 1.2.2 evaluation gates every OSCAL emitter.** OSCAL
   1.2.2 released 2026-04-30; whether the cycle's OSCAL output (AR, POA&M,
   traceability profile, catalogs) moves to 1.2.2 or stays on 1.2.1 must be
   decided **before** new OSCAL-emitting features are built, or they get
   built twice. The evaluation is an assessment with a written verdict, not
   a committed adoption.
2. **VEX + Rekor and SLSA VSA ride the same attestation surface** — one
   signing/attestation wave, not two.
3. **SP 800-218A pairs with the `docs/ai-coding-policy.md` template** — the
   catalog and the template ship together (the dogfood narrative depends on
   both).
4. **Two standing commitments are carried INTO this cycle and cannot be
   dropped**: OMB M-25-21 full minimum-practice tracking (+ the M-25-22
   procurement-lifecycle surface) — v0.10.12 only *documented* the seven
   practices — and the 4-phase AI-governance crosswalk enrichment.
5. The hygiene track has no wave dependency — small, independently
   mergeable PRs, front-loaded early in the cycle.

## Wave 1 — OSCAL 1.2.2 evaluation (decision gate)

Assess the 1.2.1 → 1.2.2 schema delta against every emitting/parsing
surface (AR exporter, POA&M, traceability profile, catalog serializations,
`oscal verify`, trestle round-trip tests). Deliverable: a written verdict —
adopt-now / defer-with-trigger — recorded in the ROADMAP entry and this
plan. **All OSCAL-emitting work below waits for this verdict.**

**VERDICT (evaluated 2026-07-10, ratified 2026-07-13):
DEFER-WITH-TRIGGER — emitted documents stay on 1.2.1.**

- **Delta**: content-free for every surface Evidentia emits. All nine
  published 1.2.2 JSON schemas are byte-identical to 1.2.1 except the
  `$id` version string; XSDs differ only in version markers (verified
  by two independent diffs of all 50 release artifacts per version).
  A valid 1.2.1 document validates unchanged under the 1.2.2 schemas.
  The only behavioral constraint changes are SSP-only
  (`validated-by`→`validation` link index; `responsible-role
  [party-uuid]` loosening) — Evidentia has no SSP emitter; any future
  SSP work must use `rel="validation"` with a local `#` href.
- **Ecosystem**: compliance-trestle v4.2.0 (locked dev dep; the
  validator the published quickstart recipe tells consumers to run)
  hard-rejects `oscal-version: 1.2.2` via `OSCAL_VERSION_REGEX
  ^1\.2\.[0-1]$`; its 1.2.2 support PR (#2216) is open/unmerged.
  oscal-cli v3.2.0 (2026-05-15) deliberately ships 1.2.1 bindings.
  Only NIST's own oscal-content is on 1.2.2. Adopting now = breaking
  our own B7 round-trip tests and consumers' validation, for zero
  capability gain.
- **Adoption triggers**: (T1) a trestle release accepts 1.2.2 →
  adopt; (T2) corroborate at adopt time that oscal-cli ships 1.2.2
  bindings; (T3) an external consumer/regulator requires 1.2.2; (T4)
  standing re-check at each quarterly practice-delta pass (next
  2026-10-01) so the defer cannot rot.
- **Adopt-time touchpoints** (mechanical): `OSCAL_SCHEMA_VERSION` in
  `evidentia_core/oscal/_version.py` (single source for all four
  emitters) + its docstring; the hardcoded asserts in
  `test_poam_exporter.py` / `test_osps_baseline.py`; the committed
  `osps-baseline.oscal.json` (no generator script — manual regen) and
  `examples/fda-524b-DEMO-example-assessment.oscal.json`; the
  orphaned UI fixture `oscal-fixtures.ts` (delete instead); and the
  current-version doc claims (README, quickstart, integration-survey,
  positioning-and-value, capability-matrix, contributing-a-catalog,
  osps-baseline-mapping, catalog-engine, conference-outreach,
  `regenerate_manifest.py` comment). Parse/verify surfaces need
  nothing (catalog loader, profile resolver, component-definition
  ingest, and `oscal verify` are version-agnostic — verified zero
  `oscal-version` reads).
