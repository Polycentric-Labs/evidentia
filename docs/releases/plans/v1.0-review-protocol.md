## 1. Purpose and non-goals

Turn the maintainer's decision — *v1.0 ships only after independent
professionals have thoroughly vetted one final, unchanged frozen
candidate* — into auditable evidence.

**Non-goals**: marketing, testimonials, endorsements, or validation of
anything outside the open-source release.

## 2. Reviewer coverage (minimum)

Reviewers are identified by **role, never by name** in this document.

| Lens | Role | Must be independent of | Deliverable |
|---|---|---|---|
| **A. GRC / federal-compliance domain expert** | practitioner who has produced or consumed SSPs, POA&Ms, ConMon evidence, OSCAL or FedRAMP artifacts | Evidentia authorship | correctness + auditability findings against the scenario pack |
| **B. Hands-on operator** | someone who installs from PyPI/GHCR on their own machine or CI, offline path included | the maintainer's machines | usability + install/upgrade/offline findings, plus a reproducible environment record |
| **C. Security / supply-chain reviewer** (sought) | AppSec or supply-chain engineer | the release pipeline | threat-model + release-integrity findings (SBOM, attestations, signing, container) |

**A + B are the floor; C is sought.** One person may not cover two
lenses.

## 3. Frozen candidate rule

- Reviewers receive **one** identified release candidate: commit SHA,
  tag (`v1.0.0-rc.N`), artifact digests (8 wheels, container image,
  SBOM), and the scenario-pack version.
- **Any** change to reviewed behaviour or artifacts produces a new
  `rc.N+1`, and the affected lens repeats its scope.
- Release only the final unchanged reviewed candidate — the release is a
  re-tag of the same tree as `v1.0.0`, artifacts rebuilt by `release.yml`
  and re-verified byte-equivalent where reproducible, hash-recorded where
  not.
- Candidate identity is recorded in the ledger **before** outreach.

## 4. Scenario pack

Representative workflows. Each ships with steps, fixture inputs, expected
artifacts and exit codes, and explicit "what would be a release-blocking
failure" wording. Reviewers record actual vs expected.

1. **Catalog / control lookup** — `catalog list`, `catalog show`,
   crosswalk query.
2. **Inventory → gap analysis → report** — CLI + API + GUI parity check
   over the same inventory.
3. **OSCAL emit + verify** — `oscal export`, signed AR, `oscal verify`
   round-trip, trestle load.
4. **POA&M lifecycle + ConMon** — `poam create` / `verify`,
   `conmon check` / `watch`, and `conmon ksi` SDR emit validating against
   the vendored CR26 schemas — both the `keySecurityIndicators` block and
   (v0.12.0+) the `fedRampRequirements` block, with the KSI and FRR
   coverage reports read as the completeness signal.
5. **One collector end-to-end** — reviewer's choice (GitHub or a SQL
   adapter) → OCSF / SARIF outputs.
6. **Offline / air-gap path** — `--offline`, DSSE/keysign signing, no
   network egress observed.
7. **Upgrade + deprecation guidance** — install v0.11.x → v1.0.0-rc,
   exercise every warning path, and confirm the removals match
   [`deprecation-calendar.md`](../../deprecation-calendar.md).
8. **Container path** — GHCR pull, `docker run … doctor`, health,
   read-only rootfs behaviour.

## 5. Structured rubric

Applied per scenario, per lens.

| Dimension | 1 (blocking) | 2 (must-fix pre-1.0) | 3 (acceptable, deferral allowed) | 4 (good) |
|---|---|---|---|---|
| **Correctness** | wrong compliance result / invalid OSCAL | wrong in an edge case | cosmetic inaccuracy | correct |
| **Usability** | operator cannot complete the workflow | completes with an undocumented workaround | rough but documented | smooth |
| **Auditability** | output cannot be traced to inputs/rules | traceable with effort | traceable | traceable + provenance stamped |
| **Interoperability** | consumer tool rejects the artifact | accepted with warnings | accepted | accepted + validated |
| **Security expectations** | secret, unsafe default, or egress found | hardening gap with mitigation | advisory | none |
| **Documentation sufficiency** | doc contradicts behaviour | doc missing for a shipped path | doc thin | doc sufficient |
| **Production-blocking?** | yes | — | — | no |

**A score of 1 anywhere is a release-blocking finding.**

## 6. Reproducible issue ledger

One row per finding:

`id · lens · scenario · observation · environment (OS / Python / install
path / version) · steps · expected · actual · severity (rubric) · owner ·
disposition (fix / defer-with-rationale / not-a-bug) · evidence (log or
artifact hash) · reviewer confirmation (rc.N re-test result)`

Kept as a tracked CSV or Markdown file under `docs/releases/reviews/v1.0/`
once outreach starts; a local template until then. §9.3 records whether
it is tracked in-repo from day one.

## 7. Exit rule

v1.0.0 releases when **all** of the following hold:

- Zero unresolved severity-1 findings, and every severity-2 finding
  either fixed or explicitly deferred with a publicly appropriate
  rationale recorded in the ledger.
- API/schema drift gates and the pre-release review are PROCEED-CLEAN on
  the **final** candidate.
- Each lens confirms its scope on the final **unchanged** candidate.
- The maintainer explicitly approves the release action.

## 8. Rules of engagement

**Acceptance testing is not marketing permission.**

- Reviewer names, affiliations, and quotes are **never** published unless
  separately and explicitly authorized in writing by that reviewer.
- No compensation is implied, and no NDA is needed — reviewers work only
  with public open-source artifacts.
- Communication templates and any intake form are separate deliverables
  requiring maintainer approval before any external message is sent.
