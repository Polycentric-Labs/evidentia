## Items

### A — eval CLI auto-sign: OIDC graceful degrade

The product fix behind the v0.10.8 test fix (F-V108-CI1). `_resolve_sign`
(`packages/evidentia/src/evidentia/cli/eval.py`) auto-signs when
`GITHUB_ACTIONS=true` and sigstore is importable, but never checks OIDC-token
*obtainability* — so `evidentia eval … --output` crashes with
`SigstoreSigningError` in any CI job lacking `id-token: write` (exactly the
release gate job's permission set).

**Design:** only the auto-detect branch changes. It now additionally requires
`ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_URL` to be
present (GitHub sets both iff the job has `id-token: write`). When CI is
detected but no token is obtainable: return False and warn on stderr
("CI detected but no OIDC token (`id-token: write` missing); writing unsigned
output; pass `--sign` to force"). An **explicit** `--sign` keeps the current
attempt-and-raise behavior — when the user demanded signing, honest failure
beats silent degrade. New unit tests cover the tri-state × token-presence
matrix; the v0.10.8 hermetic autouse fixture stays.

### B — SF-V108-3: `check_uv_lock_pin_drift` per-commit attribution

The aggregate `base..tip` diff misattributes a separately-committed third-party
dependency bump to the workspace version bump when both sit in one push range
(the v0.10.8 false positive that forced a logged bypass).

**Design:** walk each commit in the range that touches `uv.lock` and diff
`C^ → C`, reusing the existing `workspace_bumped` / `third_party_drift`
classifiers per commit. Fail only when a *single commit* both bumps workspace
versions and moves a third-party pin. The exact v0.10.8 shape (a dep-bump
commit followed by a clean version-bump commit) becomes a must-pass regression
test; a true positive (one commit doing both) stays red.

### C — SF-V108-4: scaffolder G4 defaults to the gitleaks binary (skill-side)

The `release-safeguards-scaffolder` G4 template scaffolds the gitleaks
*action*, which requires a paid license on organization-owned repos (the
post-v0.10.8 red-workflow bug). Fix lives in the skill, not this repo: the
template defaults to the MIT-licensed gitleaks *binary* (version-pinned +
SHA256-verified, mirroring this repo's `secret-scan.yml`), with an
org-detection note about the action's license wall. No release coupling.

### D — parity gate: advisory → blocking, including the tag-time gate

Two changes: (1) remove the `|| echo "::warning::…"` escape from
`.github/workflows/parity.yml` so the workflow goes red on a parity
regression; (2) add a `parity` Check to `_FULL_ONLY_CHECKS` in
`scripts/run_gate_suite.py` so the tag-time release gate hard-blocks a parity
regression from reaching PyPI (gate-suite invariant tests updated). The gate
suite remains the single source of truth for release-path checks; the
standalone workflow remains the per-push early signal. Adding parity to the
branch-protection required-checks set was considered and deferred.

### E — `PoamGap` → generated `ControlGap-Output`

`PoamPage.tsx` hand-widens the hand-authored `ControlGap` mirror with
`poam_milestones?: Milestone[]`. Replace the local intersection with the
generated OpenAPI type (`components["schemas"]["ControlGap-Output"]`), which
already models the field; the `components` import path already exists in the
file.

### F — shared `lib/sse.ts`

`ExplainPage.tsx` and `RiskGeneratePage.tsx` carry functionally identical
`readSse` implementations. Extract one generic `readSse<T>(body, onEvent)` to
`packages/evidentia-ui/src/lib/sse.ts` (the established utility dir); both
pages import it. New `lib/sse.test.ts` covers frames split across chunks,
multi-`data:`-line records, and non-JSON keep-alive noise.

### G — safeguards-resweep idempotency

The quarterly workflow's existing-issue probe searches *open* issues with a
substring match, so a manually closed tracking issue resurrects on the next
scheduled run. Switch to exact-title matching across open **and** closed
issues: an open match exits 0 (already tracked); a closed match for the same
quarter exits 0 (deliberately closed — do not resurrect).

### H — aiohttp watch-item probe (serialized after the build)

The two accepted aiohttp client-cookie CVEs (`osv-scanner.toml`,
`ignoreUntil 2026-12-04`) are upstream-blocked by litellm's exact
`aiohttp==3.13.4` pin. Probe: check the latest litellm release's aiohttp
constraint via PyPI metadata; if it allows ≥ 3.14.0, run
`uv lock --upgrade-package litellm`, drop both `[[IgnoredVulns]]` entries, and
re-validate (osv + full tests). Otherwise revert the lock and the watch-item
stands.

## Execution

Four parallel build agents on disjoint file domains, each TDD-first with its
focused tests: (1) Python product — A; (2) release tooling — B; (3)
gates/workflows — D + G; (4) UI — E + F. Items C and H run serialized
afterward (C is outside the repo; H mutates `uv.lock`). Single-writer
integration: CHANGELOG + commits happen at integration, not per-agent.

Gates before tag (per `/pre-release-review` v5.2): full local gate suite plus
**full-extras pytest** (`uv run --all-extras --all-packages python -m pytest
tests/ -q`) — the default-env run skips the eval tests, which is the exact gap
that let F-V108-CI1 reach the v0.10.8 tag-gate.
