# v1.0-prep plan — the release-candidate cycle

**Status: DRAFTED 2026-08-21 at v0.12.0 release prep; ratification is the
first item of the cycle.** This is the cycle between v0.12.0 and the v1.0.0
tag. It exists because the roadmap-currency gate requires exactly one open
cycle with an on-disk plan, and because the v1.0 acceptance program has
enough moving parts to deserve its own sequencing.

Scope philosophy: **CONVERGE, not expand.** Nothing new is built for its own
sake. Every item either closes a v1.0 acceptance gate, executes a decision the
freeze-candidates register already holds open, or removes something the
deprecation calendar scheduled for v1.0.0. Feature expansion waits for v1.1.

## Sequencing

1. **Ratify this plan** (maintainer) and settle the §9 protocol questions and
   the §1g / §3 / §4 DECIDE items from the freeze register. These are
   decisions, not builds; they gate everything below.
2. **Freeze execution** (one PR): promote the FREEZE env-var groups and the
   v0.11 federal library surfaces into `api-stability.md`; the
   `check_public_surface` gate enforces the result on every push from then
   on. Additive, contract `none`.
3. **`Finding` rename** (one PR): the three-step plan. The openapi drift gate
   must show a zero schema diff, which is the whole point of step 2's
   `ConfigDict(title=…)`. Contract `additive` (a new canonical class name;
   the old name keeps working with a warning).
4. **Frozen candidate**: tag `v1.0.0-rc.1` on a commit with steps 2 and 3
   landed. Record its identity in the ledger **before** any outreach, per
   protocol §3.
5. **Reviewer outreach** (explicit maintainer gate; communications template is
   a separate deliverable). Scenario pack + fixtures ship with the rc.
6. **Review loop**: findings → ledger → fix or defer-with-rationale → new
   `rc.N` when reviewed behaviour changes; each affected lens repeats.
7. **Scheduled removals** land in the final rc, each RED-first with its
   calendar row moved to "Recently removed".
8. **Exit**: protocol §7 holds on the final unchanged candidate → `v1.0.0` is
   a re-tag of that tree; post-tag verification; the arXiv preprint skeleton
   (pre-1.0 priority artifact, `.local/`) is the maintainer's separate call.

## Open questions (for ratification)

1. Does the rc line live on `main` (tags only) or on a release branch?
   `main`-only keeps the merge queue as the single gate; a branch lets
   v1.1 work start before v1.0.0 tags.
2. How many `rc.N` rounds before scope is re-cut rather than re-frozen?
   (Protocol §9.2.)
3. Is the `SecurityFinding` alias kept into v1.x (cheap, spares integrators
   a second migration) or removed at v1.0.0 as the calendar says?
